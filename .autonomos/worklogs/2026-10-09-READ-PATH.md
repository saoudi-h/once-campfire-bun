# Worklog — READ-PATH profiling after PERF-22 (task open)

## Question

room_show is at 91% of Rust, messages_page at 72%. Is the
remaining gap code (fixable) or shape (bounded by response
size / runtime)? Profiled before optimizing.

## Method

Probe (removed after use): seed 100 messages, single process,
warm page + gzip caches, then timed components in isolation
(2000 iterations, JIT-warmed) plus the full request.
`app.fetch()` (no socket) isolates the application cost from
transport; `GET /up` gives the transport + dispatch baseline.

## Hit-path decomposition (room page, 100 messages)

| measure | µs |
|---|---|
| FULL room-page GET (HTTP, gzip) | 415 |
| GET /up (transport + dispatch baseline) | 70 |
| APP-ONLY room-page hit (`app.fetch`, no socket) | **138** |
| buildReq + auth (components summed) | ~85 |
| — of which crypto (decryptCookie 12, verifyCookie 11, maskCsrf 4, randomBytes ~2) | ~29 |
| — of which 4 SELECTs (sessions+users, user, account, bans) | ~14 |
| — of which URL/headers/parseCookies/misc | ~42 |

Remaining app cost beyond auth (~53µs): pageGeneration PRAGMA,
ticket + readPage LRU, res facade, finalize, gzip lookup
(O(1) — V8 caches the string hash, same instance from the page
cache), new Response.

Findings:
- The gzip cache keyed by the full body string is NOT a cost:
  a page-cache hit returns the same string instance, V8 caches
  its hash code, Map.get is O(1) with pointer equality.
  (Supersedes the PERF-20 suspect list.)
- Transport dominates the single-process number (~277µs of
  415µs) but is parallelized across workers in the official
  bench (loadgen is separate); the bench-relevant cost is the
  138µs application path.
- messages_page at 72% is a response-size effect (its body is
  larger than room_show's), not a lookup-path cost — same hit
  path, more bytes per worker.

## Lever candidates (measured, honest)

1. **Session cache (cookie → session+user rows)**: would save
   ~34µs (crypto + 2 SELECTs) = ~25% of the application cost.
   NOT adopted: it opens a revocation window (logout, session
   deletion) that fresh-per-request auth does not have. Rust
   also authenticates fresh on every lookup ("Authentication
   and room access run before every lookup") — this would be
   a behavioral and security divergence. User decision needed
   before any such change.
2. **Generation-invalidated account/user row cache**: saves
   ~10µs (~7%). Safe (any write bumps the generation) but
   small; the rows are also touched by nothing else.
3. Accept the 9% room gap: it is the JS runtime paying for
   fresh auth (Rails/Rust parity behavior) that Rust
   performs natively.

## Recommendation

No cheap win remains. The only material lever is the session
cache, which trades a revocation window for ~25% of the
application hit-path cost (maybe +2-4% on room_show in the
official bench, less elsewhere). Recommend NOT taking it
without an explicit user decision; the mission is to present
the port at its best, and a security divergence is the wrong
trade for a single-digit percent.
