# Worklog — PERF-21: image fallback matrix + compile stacking + canary adoption

Follow-up to PERF-17/18/19/20. User corrections integrated mid-task:
1.4.3 was never stable — the **canary is the usable target** (PERF-20's
"waiting for stable" framing was mine, corrected), and every remaining
Bun/Elysia production lever had to be tested from the official docs.

## 1. Image: fallback matrix measured, bug fixed, routing reworked

Micro-matrix on the real code path (`transformImage`, 1200x800 fit,
5-run avg) plus `imageMetadata`, all input formats:

| input → output | before (auto) | sharp | after |
|---|---|---|---|
| jpg→jpeg | 14.5ms (Bun) | 14.7 | Bun, parity |
| jpg→png | 128ms (Bun!) | 36 | **sharp, 3.5x** |
| jpg→webp | 65ms (sharp) | 66 | sharp (same engine) |
| png→jpeg | 23.7 (Bun) | 20.5 | Bun, parity-ish |
| webp→jpeg | 19.7 (Bun!) | 5.3 | **sharp, 3.7x** |
| gif→jpeg | 2.1 (Bun) | 3.2 | Bun, faster |
| tiff→jpeg/png | **ERR (500!)** | 15/36 | **sharp (bug fix)** |
| avif→jpeg/png | **ERR (500!)** | 39/59 | **sharp (bug fix)** |
| metadata | all <1.5ms both | — | Bun first, sharp fallback |

Findings shipped (`src/image.ts`, `src/storage.ts`):
- **Correctness bug:** TIFF/AVIF input → JPEG/PNG output threw
  `ERR_IMAGE_FORMAT_UNSUPPORTED` instead of falling back (the catch
  only handled `ERR_IMAGE_DECODE_FAILED`). Any TIFF/AVIF upload
  requesting a JPEG/PNG variant 500'd. Fixed + regression test
  (`test/storage.test.ts`: tiff/avif/webp → jpeg variants).
- **PNG output routed back to sharp** (Bun's PNG encoder 2-3.5x
  slower at both 1200 and 400px). Bun path is now JPEG-output only.
- **WebP input routed straight to sharp** via a new
  `inputFormat` hint (passed from `blob.content_type` in `variant()`):
  19.7 → ~5.5ms. Try-Bun-first can't catch "slow success", so the
  hint (zero I/O) was required.
- **`sharpen: true` dropped from `variant()`**: the reference Rails
  app uses plain `resize_to_limit` nowhere sharpened — it was an
  Express-port artifact costing ~13ms on the sharp path (measured
  13.5 → 26.3ms). Dropping it improves Rails parity *and* speed. Bun
  path never sharpened (no sharpen op in Bun.Image).
- **`maxPixels: 100_000_000` pinned** on Bun constructors for parity
  with sharp's `limitInputPixels` (Bun default 268M is looser).
- **Dead `import sharp from "sharp"` removed** from `src/storage.ts`
  (imported but never used — contradicted the "lazy sharp" claim,
  forced the bundler to include it).
- Official Linux matrix confirmed in code comments: JPEG/PNG/WebP
  full support; TIFF/AVIF/HEIC undecodable; no GIF/TIFF/AVIF encoder.

## 2. Compile: embedded binary works, sharp native binding blocks prod

New `bin/build-binary.js` (Bun.build API) with production flags from
the official docs: `--compile --minify --target bun-linux-x64
--define NODE_ENV=production --asset ×7` (+ `src/data.ts` EMBED_MAP
+ `src/public.ts`/`src/app.ts` routed through `dataPath`).

- **CLI `--asset` silently drops directory assets** (canary bug):
  repeated `--asset dir` only embedded the first dir + files; the
  Bun.build `assets:[]` API embeds all 547. Used the API.
- **`--asset` strips each root** (`./assets/generated/x` embeds as
  `generated/x`): repo-relative paths unachievable, hence EMBED_MAP.
  Also fixed: `dataPath` now splits joined segments (the logo/sw 404s
  came from `dataPath("a/b/c")` never matching the map).
- **Build A (embedded) fully verified**: boot 108ms, room page
  ~6.2-6.8k rps ≈ interpreted (~6.4k, within noise), RSS ~96-105MB ≈
  interpreted, all probes 200 from `$bunfs` (page, logo,
  service-worker, digested asset). Data-dir layout (Build B) not
  re-measured — PERF-19 already showed neutral, and A removes the
  deploy complexity.
- **`--bytecode`: tried, measured zero, dropped.** The bundler rejects
  top-level await in `src/server.ts`; wrapping boot in `main()` (done,
  verified multi-worker boot, then reverted) unlocked the build, but
  boot 108→107ms, rps and RSS identical, +5.4MB binary. Our boot is
  DB-bound, not parse-bound. PGO/jitPolicy depend on bytecode →
  dropped with it. Recipe kept here for newer canaries.
- **BLOCKER (decisive): sharp's native binding doesn't load in the
  binary** ("Could not load the sharp module", bundled JS OK). And
  `--external sharp` can't resolve outside `$bunfs` (NODE_PATH
  ignored). Consequence: every sharp path (PNG/WebP/GIF/TIFF/AVIF
  variants, account logos, webp avatars) 500s in a pure binary.
  **Binary NOT adopted for production.** Dockerfile unchanged in this
  respect; revisit when Bun fixes `.node` bundling for sharp.

## 3. Canary: A/B green, pinned in Dockerfile

`campfire-bun:perf-stable` (oven/bun:1 = 1.4.2) vs
`campfire-bun:perf-canary` (1.4.3-canary.1+620b50f6a = local
toolchain), same app code, fresh seed/round, WEB_WORKERS=4, server
cpus 8-11, loadgen cpus 12-15, room page c=8/800req:

| round | stable rps | canary rps |
|---|---|---|
| 1 | 8584/8581/5800* | 5839/7622/7278 |
| 2 | 7095/8627/8858 | 5484/6902/9168 |
| RSS | 239/252 MB | 217/226 MB |

\*cold run1 + one dip; ranges overlap fully → throughput neutral
(within noise, both climb as caches warm). RSS: canary **−10%**
(245 → 221MB avg), same direction as PERF-17's −7%. Zero errors.
**Dockerfile `FROM oven/bun:1` → `oven/bun:canary`** (floating,
same policy as before).

## Incidents & lessons (cheap, saved for next time)

- Bench scripts in /tmp resolve bare imports from the script's dir:
  a *different* sharp copy + Bun.Image deadlocked at 0 CPU (futex).
  Symlink project `node_modules` into the scratch dir (kept at
  /tmp/opencode/node_modules — outside the repo).
- Never build/run heavy jobs during a bench window (explains one
  4732 dip); interleave A/B rounds, compare medians, distrust run1.
- `bun --revision`, not `--version`, identifies canaries
  (AGENT.md updated in PERF-20).
