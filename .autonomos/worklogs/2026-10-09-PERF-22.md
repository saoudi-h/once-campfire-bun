# Worklog — PERF-22: Rust Oct-7 response cache port (generation tickets)

## Context

Rust's Oct-7 upgrade (d09811c whole-response caching + 4d23733 +
86bc216 + rowid search b1d751b) doubled their read throughput
(room 17k→36k on the official harness). Our versioned-key page
cache (PERF-01/05) pays 3–6 version SELECTs before every cache
lookup. PERF-22 ports the Rust design
(`crates/campfire/src/response_cache.rs`: Observer + Ticket +
Snapshot) to the three cached page routes.

## Design (mirrors response_cache.rs)

- **Observer:** a separate read-only SQLite connection per
  process polls `PRAGMA data_version` pre-auth. CRITICAL
  SEMANTICS (verified empirically on this host): data_version
  only advances when the file changes as seen by ANOTHER
  connection — the write connection never observes its own
  commits (WAL commit → unchanged, even after PASSIVE
  checkpoint; separate connection same-process → changed;
  cross-process → changed). The single-write-connection
  architecture made the naive port (probing `db()`) silently
  broken: local writes (edits, room updates, memberships…)
  would never invalidate the cache. The observer connection is
  the fix — exactly Rust's design (their observer is also a
  separate connection from their writer).
- **Ticket:** key = `[generation, ...non-DB inputs]`. Any
  commit anywhere makes every entry unreachable at once, so the
  version SELECTs (room/user/membership/account rows, logo
  presence, matched-message versions, recent-search state) are
  dropped from key construction AND from the pre-lookup path.
  Converted routes = Rust's endpoint set: rooms#show,
  messages#index (room page), users/sidebars#show,
  searches#index.
- **Snapshot:** generation captured in `runHandlers` BEFORE
  auth — a revocation landing mid-auth cannot serve a cached
  page (Rust's pre-auth Snapshot).
- **Admit re-check:** a commit during render never files a
  pre-commit render under the new generation (Rust's `put`).
- **TTL 15s:** time-dependent links/dates expire even without
  a commit (Rust parity; the old versioned keys had no TTL).
- **Eligibility:** GET/HEAD only, no Range/Upgrade, no
  no-cache/no-store request directives (Rust's
  `eligible_request`).
- **Deviation:** the message-fragment cache stays
  per-message-versioned — finer-grained than Rust's
  generation-namespaced fragments, strictly less invalidation.
- Observer failure (or `:memory:`) disables the page cache
  (bypass, never stale) — Rust's observer-error policy.

## Bug found and fixed during the port

The initial WIP probed data_version on the write connection.
Regression tests now pin the semantics: same-process write →
room page and search page must serve fresh content; hit/miss
accounting via `pageCacheStats` (1 entry on a hit, new
generation key after a write).

## Measurement (lightweight protocol: single process, c=8,
## 800 reqs/run, 3 runs, warmup before each run, fresh seed,
## gzip, single session = 100% hit rate)

| route  | before (versioned keys) | after (tickets) | delta | counted queries/req |
|--------|------------------------|-----------------|-------|---------------------|
| room   | 5457                   | 5704            | +4.5% | 8 → 5               |
| sidebar| 6290                   | 8923            | +42%  | 10 → 4              |
| search | 1804                   | 1966            | +9%   | 9 → 4               |

Sidebar wins biggest: its versioned key ran 5 SELECTs
(incl. the nested direct-user query, the fattest). The room
page is response-size-bound (~500KB render, gzip), so the 3
saved SELECTs move it less. Absolute numbers are host-specific
(ratios only, same setup). The official harness (multi-session,
4 workers, c=16) will give the definitive elysia-vs-rust table.
