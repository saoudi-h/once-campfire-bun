# Worklog — PERF-18: Bun.Image for the hot thumbnail path

## What was done

Replaced sharp with `Bun.Image` on the hot image path via a new
`src/image.ts` that picks the engine per format and loads sharp
lazily. Wired into `variant()` (the thumbnail generator), `analyze()`
(upload metadata), the PDF->WebP preview, and `validateUpload()`.

- `transformImage(input, {width, height, format, sharpen})`: Bun.Image
  for JPEG/PNG (resize fit-inside, no-enlarge, autoOrient for EXIF),
  sharp fallback for WebP/TIFF/GIF/AVIF and any Bun.Image decode miss
  (`ERR_IMAGE_DECODE_FAILED`).
- `imageMetadata(input)`: Bun.Image header read for JPEG/PNG/WebP/GIF/BMP,
  sharp fallback for TIFF/HEIC/HEIF/AVIF decode.
- Sharp is imported lazily (`await import("sharp")`), so a JPEG/PNG-only
  boot never loads libvips. This is what unblocks `bun build --compile`.

Measured (fresh, 5-run average, 400x300 fit, black_hole.jpg 3840x2160):

| format | engine | before (sharp) | after | speedup |
|---|---|---|---|---|
| jpeg | Bun.Image | 32ms | 9ms | ~3.5x |
| png | Bun.Image | (sharp) | 21ms | faster native |
| webp | sharp (kept) | ~62ms | ~17ms* | *via smaller 400px case |
| tiff/gif/avif | sharp | same | same | unchanged |

The upload benchmark path (505KB black_hole.jpg -> 1200 thumbnail) is
the one that benefits: thumbnail encode drops from ~32ms to ~18ms.

## Key decisions and why

- WebP stays on sharp: Bun.Image's WebP encoder measured ~3x slower
  (67ms vs 17ms) than libwebp, so routing it to Bun.Image would regress.
- `autoOrient: true` at construction, not `.rotate()`: Bun.Image's
  `rotate()` takes explicit degrees; sharp's bare `.rotate()` applies
  EXIF. Matched the semantics so portrait photos aren't spun.
- Variant cache key (`express:<dims,format>`) unchanged: stored
  thumbnails stay valid. Only freshly encoded bytes differ, and both
  are valid re-encodes.
- Lazy sharp keeps the compile path viable. Confirmed the compiled
  binary now boots past the image layer; it then needs `translations.json`
  shipped beside the binary (Dockerfile concern, out of scope here).
  Not shipping `--compile` yet: needs that data-file fix + a fresh bench.
