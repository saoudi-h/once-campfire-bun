## What was done

Re-ran the official verification harness
(`once-campfire-verification/bench/compare.rb` via dockerized
ruby) after the PERF-22 generation-ticket port, to measure the
read-path gains on the definitive elysia-vs-rust table.

Runner: `docker run --rm --network host -u 1000:1000
--group-add 966 -v /var/run/docker.sock:/var/run/docker.sock
-v /home/hakim/projects:/home/hakim/projects -w .../once-campfire-verification
bench-ruby:1 ruby bench/compare.rb --apps rust,elysia
--rounds 3 --duration 8 --concurrencies 16 --cpus 8-11
--client-cpus 12-15` with `ELYSIA_BENCH_ENV={"WEB_WORKERS":"4"}`.

Pitfalls solved (worth keeping for next time):
- The bench-ruby container needs `--network host`: the loadgen
  runs inside it and the app containers share the host network
  (127.0.0.1:25130), so bridge networking cannot reach them.
- The container runs as uid 1000 with `--group-add 966` (docker
  socket gid) — file ownership of results/seed copies.
- The runner shells out to `ffprobe` for the avatar pixel
  contract; the bench-ruby image lacked it. Installed
  (ffmpeg) and committed the image as bench-ruby:1.
- `ELYSIA_BENCH_ENV` (JSON, merged into the container env by
  compare.rb) is how WEB_WORKERS=4 reaches our image — the
  default env file is Rails-oriented and sets nothing for us.
  Without it the app boots with 1 worker and reads collapse
  (26k→8k rps on room_show). Always pass it.
- Images are NOT built by compare.rb: build
  `once-campfire-elysia:app` from ../once-campfire-elysia
  (symlink to this repo) beforehand.
- The runner fails closed: completion = all route contracts +
  write audits green (zero errors).

Results dir: `.../results/20261009-105044-1/`

## Watch item (post_message), stated precisely

Across the three runs of today (073639: elysia post
2049→1752→1455 over its rounds; 075722: 1860→1485→1693;
now: 1753→1113→942) elysia post rps trends DOWN within a run
on FRESH databases per round, while rust shows noise without
trend. Same binary cannot regress; a fresh DB per round
removes the write-path settling explanation. Remaining
hypotheses: (a) host-side aging under sustained load (CPU
frequency/thermal, page-cache pressure) — supported by the
uniform shift seen across ALL routes this morning; (b) a
write-path property that only elysia exercises (writer IPC
lock, WAL growth over the round) — not yet isolated. Next
step when a definitive read is needed: run post-only with
per-second rps tracing + CPU frequency logging, interleaved
against rust. Not a regression proof; do not chase code
before measuring.

## Sharp / Bun.Image / Rust comparison (user question)

Rust ports libvips (native binding, `crates/storage/src/vips.rs`)
like the C port. We run Bun.Image for JPEG-out + sharp for
everything else — and sharp IS libvips bindings, so native
coverage is comparable. What Bun.Image cannot do on Linux:
decode TIFF/AVIF/HEIC, encode PNG at competitive speed
(2–3.5x slower than sharp's libvips encoder), encode
GIF/TIFF/AVIF. Image work is upload-time only (variants are
pre-generated and stored); the bench reads serve bytes, not
processing. No port action needed; keep the measured matrix
in PERF-21.
