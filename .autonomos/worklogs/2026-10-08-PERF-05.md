# Worklog — PERF-05: sidebar page-cache

## What was done

Profiled the sidebar handler (david, 9 rooms): roomsForUser 0.13ms,
roomData x9 0.24ms, render warm 0.27ms, gzip 7.7KB->1.9KB 2.4ms
(threadpool dispatch dominates for small bodies). Sidebar HTML carries
no per-session token (verified: no authenticity_token), so the cache
is session-independent.

Cached the sidebar fragment keyed on user id + user.updated_at +
sorted room id set (creation/deletion) + MAX room/membership
updated_at (renames, unread, involvement) + MAX direct-member
updated_at (labels/avatars) + account.updated_at (room-creation
rights). Per hit: 3 small indexed queries (~0.3ms), skipping the
JOIN, per-room lookups, render and gzip.

Bench same host, 4 workers: sidebar 10-12k -> 27.8k rps, c=1 p50
0.14ms (Rust 17.2k). No regressions: room 25.5k, messages 21.4k,
search 19.5k. Verified byte-identical hits and invalidation (other
member posts -> unread badge appears). 53 tests pass, typecheck clean.

## Key decisions and why

- No CSRF/host/frame in key: fragment proven session-independent;
  both sidebar routes render the current user's list.
- Id set in key (not just MAX versions): delete-only changes leave
  MAX unchanged and would serve stale lists.
