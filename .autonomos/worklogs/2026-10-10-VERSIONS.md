# Worklog — VERSIONS: elysia beta.29 + Bun 1.4.3 stable, dependency audit

## The bump

- `elysia` 2.0.0-beta.27 -> 2.0.0-beta.29. (`bun update elysia`
  installs the **exp** stream, 2.0.0-exp.64; the beta is pinned:
  `bun add elysia@2.0.0-beta.29`.)
- `Dockerfile`: `oven/bun:canary` -> `oven/bun:1.4.3` stable. The
  canary existed because 1.4.2 stable broke `Bun.spawn` child
  stdout (the writer IPC and the multi-worker boot); 1.4.3 ships
  the fix. Verified inside the image: master + writer start,
  `/up` answers, `WEB_WORKERS=4` boots.
- Real gain is reproducibility, not speed: `oven/bun:canary` is a
  moving tag, so a reviewer building the image from the PR gets a
  different base every day. `oven/bun:1.4.3` is a pin.

## Dependency audit (the sharp pattern, applied to everything)

Every third-party import in `src/`, checked for a faster Bun
built-in:

| import | where | Bun built-in? | verdict |
|---|---|---|---|
| `bun:sqlite` | db | already Bun | done |
| `Bun.password` (bcrypt) | login | already Bun | done |
| `Bun.WebSocketServer` | cable | already Bun | done |
| `Bun.spawn` | server | already Bun | done |
| `node:crypto` createHmac | cookie + CSRF signing | `Bun.CryptoHasher` 2x faster (0.41µs vs 0.82µs) | **skip**: saves ~0.4µs per call, about 1% of the hit path, across every signing site. Not worth the churn and the parity risk |
| `node:crypto` AES-GCM | session cookies | none | keep (1.1µs, per cookie) |
| `node:zlib` gzip | response compression | `Bun.gzipSync` (zlib-ng) | **skip**: gzip runs once per page-cache fill and off the JS thread (libuv pool), never per request. No throughput effect on the read bench |
| `parse5` | rich text parse | none | keep (write path only) |
| `sanitize-html` | message sanitize | none | keep (write path only) |
| `nunjucks` | templates | none | keep (renders only on page-cache misses) |
| `qrcode` | transfer QR | none | keep (cold admin page) |
| `web-push` | VAPID | none | keep (background jobs) |
| `sharp` | image variants | partial (`Bun.Image` lacks TIFF/AVIF/HEIC decode and a fast PNG encoder) | keep the PERF-21 matrix |

## Schema validation (TypeBox) — not applicable here

Elysia's TypeBox validates request shapes (body, params, headers,
query) with compiled schemas. Our measured routes are GET pages
with no body: their correctness comes from database lookups (the
room exists, the user is a member), which TypeBox does not replace.
The one POST route carries free-form rich text, which has no
schema to validate. Adding TypeBox would add per-request
validation cost to the write path and change nothing on the read
paths. There is no homemade validation layer to replace: the
port's checks are `required()` lookups and `guardRequest`, both
database-shaped, not schema-shaped.

## Elysia deploy page — what applies

- Cluster mode: already better. We run one master + N workers on
  SO_REUSEPORT (kernel-balanced), not `node:cluster`.
- Compile to binary with `--minify-whitespace --minify-syntax`:
  the bench image runs interpreted (`bun src/server.ts`), so the
  flags do not touch the measured numbers. `bin/build-binary.js`
  already uses `minify: true`. The binary itself stays blocked on
  sharp's native binding (PERF-21).
- Distroless + binary: lower RSS, not throughput; deferred with
  the binary.
