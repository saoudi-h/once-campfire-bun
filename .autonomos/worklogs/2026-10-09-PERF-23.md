# Worklog — PERF-23: session cache with event-driven invalidation

## What was done

Ported the C++ implementation's per-worker session cache
(`once-campfire-cpp` docs/architecture.md section 6) to our writer
IPC. The study (STUDY-CPP) measured that cache as the one idea from
their architecture that removes real per-request work from our hit
path: ~34µs of the ~138µs application cost (cookie HMAC verify 11µs,
session decrypt 12µs, two auth SELECTs ~7µs, plus the account
singleton read).

## Design (event-driven, not TTL — the point the study flagged)

- `db.ts run()` records `(table, id)` for every write commit into a
  change journal, and bumps a write generation counter.
- The writer child broadcasts its changes to every connected worker
  over the existing newline-JSON write IPC, right after the commit
  (`{op:"changes", changes:[...]}`); `write-client.ts` receives the
  frames without disturbing the request/response channel.
- The cache (in `compat.ts`) is keyed by the raw `session_token`
  cookie value and holds the session row plus the **full users row**
  (read once at fill time — the auth JOIN is a projection, and
  handlers need `password_digest`, `updated_at`, ...; memoizing the
  projection broke handlers until this was fixed).
- Invalidation, three signals:
  1. precise `(table, id)` events → drop exactly the matching
     session or user entries (table-level events drop all of that
     table, still correct, just coarser);
  2. writer broadcasts for message creates;
  3. a `PRAGMA data_version` move with no precise event (another
     worker's local commit) → flush wholesale. Over-invalidation,
     never a stale authenticated entry.
- The account singleton memoizes behind the same invalidation.
- Bounded at 4096 entries, cleared when full (same policy as theirs).

So a logout (`DELETE FROM sessions`) or a ban (`UPDATE users`) lands
on the next request, with no window.

## Two bugs found while implementing (both would have shipped)

1. **Memoized the projection, not the row.** The auth JOIN returns
   `s.*, u.name, u.role, u.status`; handlers read the full users
   row. Symptom: a private-room POST returned 204 and the JSON
   create returned 200. Fixed by reading `SELECT * FROM users` once
   at fill time. This is why the regression tests matter.
2. **My hand-rolled preflight copy failed on avatar with the new
   official seed.** Checked unmodified code on the same seed: it
   failed worse (7 pass / 10 fail). The copy's credentials no longer
   match the rebuilt seed, so that failure was my test environment,
   not the port. The official harness preflight (`compare.rb
   --preflight`) passes 7/7 including avatar and the post-write
   audit.

## Verification

- Full suite: 8/8 files, 61+3 = 64 pass, 0 fail. Typecheck clean.
- Official harness preflight (seed 4bf9d0eb): 7/7 route checks ok,
  zero errors, post audit ok.
- New regression tests: repeated requests served from the cache;
  logout revokes the entry immediately; a user status change
  revokes it. (The first versions of these asserted the wrong thing:
  `fetch` follows redirects, so a revoked session landing on the
  login page reads as 200. They now use `redirect: "manual"` and
  assert the 302.)

## Measurement (alternating A/B, 2 rounds x 6s each, before/after
## interleaved so host drift cancels)

| route | before rps | after rps | ratio |
|---|---|---|---|
| room_show | 22889 | 23334 | 1.02x |
| messages_page | 17829 | 19846 | **1.11x** |
| sidebar | 29157 | 29076 | 1.00x |
| search | 30045 | 29695 | 0.99x |
| avatar | 83914 | 85390 | 1.02x |
| static_css | 193605 | 214166 | 1.11x* |
| up | 195431 | 211625 | 1.08x* |
| post_message | 1876 | 1649 | **0.88x** |

* `up` and `static_css` never touch the session cache, so their
+8/+11% is residual host drift: part of the read gains is noise.

Honest reading: the messages page (the heaviest auth-per-response
route) gains ~11% after drift correction; room and avatar gain
~2%; sidebar and search are flat. Writes pay ~12% for the change
broadcast, which the write path did not need before. Net: a real
but small win on the heaviest read route, a real cost on writes.

## Follow-up candidates

- The write cost: broadcast only sessions/users changes, or batch
  them (the broadcast fires per commit today).
- Room and sidebar stay flat because their hit path is dominated by
  response size, not auth — the profiling in READ-PATH already
  showed that.
