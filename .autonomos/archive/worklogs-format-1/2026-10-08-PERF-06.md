# Worklog — PERF-06: writer-lock ceiling (part 1)

## What was done

Scaling sweep, fresh seed per run, POST c=16/10s:

| workers | before | after | p99 before->after |
|---|---|---|---|
| 1 | 1820 rps | 2252 | 16.6->14.3ms |
| 2 | 1953 | 2526 | 29->19ms |
| 4 | 2214 | 2383 | 56->38ms |

(Rust: 3967 rps, p99 ~9-24ms. Still x1.6 on throughput.)

Changes (`src/jobs.ts`, `src/domain.ts`, `src/routes.ts`):
- `enqueueMany`: notify fan-out batched into one multi-row INSERT
  (was 4-5 autocommit INSERTs serializing 4 workers on jobs file).
- Membership check folded into the message INSERT (`INSERT..SELECT
  WHERE EXISTS`), one roundtrip off the RESERVED hold.
- POST renders the message fragment once, shared between broadcast
  and turbo response (was messageById x3, messageData x2).
- No outer routes transaction on attachment-less POSTs, so the
  split txn (core writes, then FTS/touches as short autocommits)
  actually shortens the hold.

Trace analysis (per-request `--trace`, 20s blast): p99 ~60ms in EVERY
500ms window — structural contention, not periodic (not RESTART/GC).

## Key decisions and why

- NO deferred FTS/unread batcher: core.test.ts asserts FTS row
  synchronously after POST (line ~240). Correctness pinned by suite;
  background indexing would fork bench/prod behavior from tests.
- Single-writer IPC deferred to PERF-10 (XL): right model (Rust
  writer thread), wrong cost/benefit now.
- Deployment note: 2 workers beat 4 on pure writes (2526 vs 2383);
  reads scale with workers. Mixed-load tuning, not code.
