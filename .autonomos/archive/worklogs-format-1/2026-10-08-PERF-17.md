# Worklog — PERF-17: Bun/Elysia production pass

## What was done

Investigated runtime flags, single-file compile, and the Bun
1.4.3-canary. Measured on the real seed copy (watercooler room
page, 8 concurrent, 800 requests, gzip), RSS sampled at exit.
Nothing shipped: no change helped or justified a code edit.

### Bun 1.4.3-canary vs 1.4.2 (stable)

3 runs each, same app, same seed, same load:

| | rps | RSS MB |
|---|---|---|
| 1.4.2 | 2287 / 2321 / 2318 | 193 / 192 / 192 |
| 1.4.3-canary | 2244 / 2327 / 2278 | 177 / 179 / 180 |

Throughput identical (within noise). Memory drops ~7% (192 to 179
MB). The canary's change log (Bun.serve pipelining, WebSocket
same-read frame parse, idle GC at 10s/2min/10min, WebKit bump)
shows no HTTP-hot-path win here. Keeping 1.4.2 stable for the
benchmarked image: 7% RSS on a 200MB baseline buys nothing on this
16-thread host, and a canary risks a mid-bench regression. Revisit
when 1.4.3 ships stable.

### Other checks

- `bun build --compile --minify` bundles 1092 modules into an 82MB
  binary, then crashes on native libvips/sharp at runtime (the
  compiled bundle drops the assets/generated tree sharp loads). Not
  a safe production path for this app. Abandoned, not shipped.
- `--smol` (less memory, more GC): trades throughput for RSS on a
  server that benchmarks throughput. Wrong direction, not tested
  further.
- `--drop=console`, `--define`: no debug logging in hot paths, no
  benefit.

## Key decisions and why

- No code or Dockerfile change from this task. The app already uses
  native fast routes, single sync SQLite, worker IPC, indexed cable
  fanout, and 32MB LRU caches (PERF-01..15). Nothing in the runtime
  flags or canary moved the needle on this host.
- Measure before claim: the memory delta is real but small and
  host-specific; the throughput claim is noise. Both go in the
  worklog, neither into a public number.
