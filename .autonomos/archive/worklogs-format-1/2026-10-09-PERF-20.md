### Elysia config audit: no further points available

Already optimal, verified in `src/app.ts`:

- `precompile: true` set (JIT warmed at listen, not on first request).
- `parse: "none"` on raw-upload routes (untouched bytes); other routes
  need `ctx.body` parsing — re-parsing manually in JS would add work,
  not remove it. The measured hot path (GET room) has no body anyway.
- AOT build plugin (`elysia/plugin/aot/bun`): per Elysia's own 2.0
  notes, it buys startup/peak-memory on **schema-heavy** apps, "not
  likely significant faster throughput". We register **zero schemas**
  (all handlers `(ctx: any)`, no validation) — nothing to precompile.
  Not adopted: build complexity for ~zero request-path gain.
- `Bun.routes`/Srvx: framework-internal, picked up via the upgrade.
- Bounding proof the framework is not the bottleneck: native `/up`
  (pure Elysia, no compat pipeline) does **~85k rps** on the same
  setup vs **~6.5k rps** for the cached room page (13x). The room-page
  cost is app code (session decrypt, compat req/res, page-cache +
  gzip-cache lookup, headers) — Elysia flag tuning cannot move it.

## Key decisions and why
