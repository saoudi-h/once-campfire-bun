(`ronakjain90/once-campfire-cpp` at `d406869`) adds the C++ port to the

## Where their speed comes from (docs/architecture.md + source)

1. **Compiled templates.** `.ct` files compile to C++ functions at
   build time (static text is memcpy'd, `SafeHtml` is a type so
   unescaped output fails to compile). No template engine runs per
   request. We run nunjucks on every cache miss (~500KB of template
   execution for a room page).
2. **Build-time schema + typed statements.** `schema_gen.py` reads
   the Rails schema into C++ structs and row readers; each SQL
   statement is a `constexpr` object with a static index into a
   per-connection array of prepared statements. No hash map, no SQL
   parsing on the hot path. We hash a SQL string per `db.query()`
   call and pay bun:sqlite's prepare path.
3. **Arena per request** (`std::pmr::monotonic_buffer_resource`),
   coroutine handlers (`Task<Response>`), one `writev` per response,
   libdeflate once per cache fill, precompressed static bodies.
4. **Session cache with event-driven invalidation** (the answer to
   the question I raised when declining our session cache): the
   writer records `tx.changed(table, id)`, publishes them to every
   worker's inbox after commit, and each worker's per-worker session
   cache drops exactly the entries whose session or user row
   changed. Revocation window = commit to inbox delivery
   (sub-millisecond, in-process), not a TTL. Correct and fast.
5. **Dependency-hash page keys** instead of row-version keys: each
   statement in a tracked scope folds (statement index, parameter
   values, digest of returned rows) into an XXH3 128-bit hash, plus
   facets for non-SQL inputs (host, browser class, format, user
   `updated_at`); a page that reads the clock is marked uncacheable.
   The key therefore contains everything the page actually read, so
   over-invalidation cannot happen. A debug build re-renders 1 cache
   hit in 16 and diffs the bytes to catch missing facets.
   Our generation-ticket design is cheaper on the hit path (one
   PRAGMA vs a per-statement hash during render) but coarser: any
   commit anywhere invalidates every page.
6. **Group-commit writer** with savepoints (`group_size`), plus
   per-request **read transactions** (BEGIN on first read, ended
   before any suspend) so a handler sees its own writes.
7. **A statement memo**: a repeated identical statement inside a
   request reuses the kept row digest without re-reading.

## What is portable to our port, ranked

| Idea | Expected gain for us | Cost | Verdict |
|---|---|---|---|
| Session cache + change events (writer broadcasts `(table,id)` over the existing Unix-socket IPC; local `run()` records changes; a generation move without a precise event drops the cache wholesale) | Removes ~34µs (crypto 23 + 2 SELECTs ~7) of the ~138µs application hit path = ~25% of app cost; likely the largest single win left | Medium: writer broadcast + invalidation + a test that a revoked session stops working immediately | **Best next candidate** |
| Memoized hot single rows (account, current user) keyed by row id, invalidated by our existing generation observer | ~8µs | Low | Cheap, do it with the session cache |
| Dependency-hash page keys | Precision under write load (cache stays warm when unrelated rows change). No gain on this bench, which is read-dominated | Medium-high (scope tracking in every handler, plus the 1-in-16 audit) | Not now |
| Group commit (retry, properly) | posts: ours 1186 vs cpp 3944 vs rust 2281. Their 1.73x rust vs our 0.52x rust says our writer IPC is the weak point, not the concept | Medium | Worth a profiled retry after the session cache |

## What is not portable

Compiled templates, arenas, coroutines, `writev`, and the C++
type system are the rest of their 3x. Bun/JS pays per-request
allocation, the compat facade, and runtime nunjucks on misses; no
porting of their template pipeline changes that inside this repo's
shape. Their design also starts "from what C++ does well", not from
the Rust structure, which is a portability lesson in itself: the
speed comes from the language substrate more than from any single
trick.

## Recommendation

Adopt the session cache with event-driven invalidation (their design,
ported to our writer IPC) as the next optimization task: it is the
one idea that removes real per-request work from our hot path
without a security regression, and it directly answers the
"session cache opens a revocation window" objection that stopped us
before. Everything else in their architecture either does not apply
(compiled templates) or does not pay on this bench (dependency
keys).
