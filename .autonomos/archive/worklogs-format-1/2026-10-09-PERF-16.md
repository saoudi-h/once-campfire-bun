# Worklog — PERF-16: thumbnail serving, measured on current code

## Verdict: premise obsolete — no change needed

Task said "GET thumb 1.3ms vs 0.2ms (redirect chain vs direct
serve)". Measured on current code (probe: one image attachment
+ pre-generated variant, single process, repeat request,
warmup 20, 300 timed):

- representation endpoint (`/rails/active_storage/representations/redirect/...`):
  **0.288 ms/req**
- blob direct serve (`/rails/active_storage/blobs/redirect/...`):
  **0.226 ms/req**

Only 0.06ms apart. The 1.3ms figure predates PERF-21: the sharp
path then carried `sharpen: true` (~13ms on variant generation)
and the old variant routing; after the fallback matrix +
sharpen removal, the repeat-request path is the fat query +
HMAC verifies + `fs.existsSync` + serve — all cheap.

An in-memory (blob_id, variation_digest) → variant-row cache
would recover maybe 0.03–0.05ms of the 0.06ms gap on a path
that is neither benchmarked nor hot (thumbnails are
browser-cached; the bench hits avatar, not representations).
Not adopted: complexity + memory for a measured ~0.05ms.

## Key facts

- Repeat requests never regenerate: the variant record lives
  in `active_storage_variant_records` (created once, keyed by
  `(blob_id, variation_digest)`).
- The representation URL is signed (blob id + variation); our
  handler serves directly (no 302 chain) for both redirect and
  proxy kinds.
- Authorization (`authorizedBlob`) must stay per-request — a
  cache must not skip it. The variant file path itself is
  immutable once generated (blob delete cascades to variants,
  so a stale path is unreachable: the blob SELECT fails first).
- First request (variant generation) is the expensive one
  (sharp/Bun.Image transform) — inherent, happens once per
  (blob, dimensions, format).
