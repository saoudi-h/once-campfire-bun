1. **Escaped message markup (major):** `{{ dot.MessagesHTML }}`
   and `{{ dot.Fragment }}` under `autoescape:true` served

   substring-on-text (passes escaped or not) and benches only check

## Inversion explained: no code regression (user challenge, same day)

User rightly refused the "noise" dismissal: old harness showed us
ahead of Rust, new one 51-73%. Triangulation (all verified today):
- PERF-13 table (old harness): room 24.4k, sidebar 26.5k, Rust 17k.
- Current code + OLD harness (re-run): room ~26k, sidebar ~20k.
- Old code (d5ba927 image) + old harness: sidebar 26.5k repro.
- Sidebar wire bytes: old 1903B vs new 5914B.

Root cause (not a regression): old sidebar responses were a bare
`<turbo-frame>` fragment (7.7KB); AUDIT-01 made plain-GET sidebar
return the FULL page (30KB) — required by Rails parity AND the
official contract (`incomplete HTML page` check). Per-byte
throughput actually ROSE (204→600MB/s). The 51% vs Rust is a
same-content comparison: genuine gap, not a regression.
(Detour: an empty-DB setup error briefly suggested a first-run
artifact — disproven by re-test with the correct DB.)
- Rust's doubling (17k→36k) = their Oct-7 response-cache upgrade
  (d09811c whole-response caching + 4d23733 + 86bc216 + rowid
  search b1d751b), landed right after our old image snapshot.
  Fair, earned, unported — prime PERF-22 study material.
- Health 6x verified legitimate: our static Response (no session,
  DB, CSRF, timestamp, negotiation) vs Rust's full-stack handler
  with content negotiation. Same contract bytes; a health check
  needs no app stack. Present with that footnote, not as a trick.
- Post halved for BOTH apps (3.9k→1.8k): new-harness write-audit
  methodology, not our code (old-harness re-run still 4.0k).
- Method note: `pkill -f <scriptname>` kills your own shell when
  the pattern is in its command line — use container names/PIDs.

## Re-run elysia-only (superseded by triangulation above)

User felt a loss vs "yesterday". Re-ran the official harness,
elysia only, identical image/seed/flags (results
`.../results/20261009-075722-1/`). Deltas of medians: room −1.9%,
messages −5.7%, sidebar −2.7%, search −1.4%, avatar −5.7%, post
−3.4%, css −8.9%, up −18.2%. First verdict was **noise, not loss**
(same binary; uniform shift; host swings ±10-15%). The deeper
triangulation above then gave the complete picture: no code
regression anywhere; sidebar explained by full-page content;
Rust's jump by their Oct-7 cache upgrade. Remaining notes:
- Same binary byte-for-byte → a code regression is impossible;
  any delta is environment or methodology.
- Uniform shift on all 8 routes (a code change moves specific
  paths). The `up` route is a static Response with no app code —
  nothing we ship can slow it 18%; only CPU steal/frequency can.
- This host routinely swings ±10-15% (documented dips across
  PERF-17/20/21; a tsc build ate 764% CPU here yesterday).
- "Yesterday's" lightweight numbers (single worker, c=8, custom
  script) are not comparable to harness numbers (4 workers, 16
  clients, 8s samples) — different setups measure different things.
- One systematic pattern across BOTH runs (not noise): post rps
  declines round over round (2049→1752→1455 then 1860→1485→1693)
  on fresh DBs each round → host-side aging under sustained load
  (thermal/page-cache) or write-path settling; rust shows noise
  without trend. Watch item for PERF-22, not a regression proof.
